# PGO experiment (negative result)

Profile-guided optimization was evaluated as the remaining compiler-level lever
for emulation-layer performance. It did **not** produce a measurable gain for
this driver, and is therefore not shipped. This document records the method and
the data so the experiment is not repeated blindly.

## Why PGO looked promising

DXVK/VKD3D and emulators spend a large share of their time in driver CPU code:
building command streams for thousands of small draws, updating descriptors and
compiling shaders with IR3. A 5–15 % improvement there would matter more than
any GPU-side tweak available to us, because the 1.5 MiB GMEM part is not
fill-rate starved in these workloads.

Mesa refuses LTO (`Building Mesa with LTO is not supported.`), but PGO is just
instrumentation flags, so it is allowed.

## Method

1. Built an instrumented driver with
   `-fprofile-instr-generate` (compile and link), same release configuration as
   the shipped build otherwise.
2. Ran a corpus on the device with `LLVM_PROFILE_FILE=/data/local/tmp/prof/%p-%m.profraw`:
   * `a22test` twice — instance/device creation, compute pipeline, image clear
     and copy, submission and fence paths;
   * `a22bench` 1920×1080 × 32 draws — tiling, render pass setup;
   * `a22bench` 64×64 × 4000 draws — draw submission hot path.
3. Merged with NDK r28c `llvm-profdata` (5.4 MB profile).
4. Rebuilt with `-fprofile-instr-use=<merged.profdata>`.
5. Ran the functional gate and benchmarked stock vs PGO, interleaved, twice.

## Results

Draw submission (64×64, 4000 draws, both samples at 736 MHz):

| Build | run 1 | run 2 |
|---|---|---|
| stock build | 1.477 ms | 1.584 ms |
| PGO | 1.492 ms | 1.478 ms |

Means 1.53 vs 1.49 ms (~3 %), but the spread between runs of the *same* build is
7 %, so this is not a signal.

1080p fill (32 draws):

| Build | run 1 | run 2 | clock |
|---|---|---|---|
| stock build | 3.886 ms | 3.924 ms | 835 MHz |
| PGO | 3.539 ms | 3.371 ms | **950 MHz** |

Normalising by frequency (950/835 = 1.138) gives stock ≈ 3.41–3.45 ms at
950 MHz — indistinguishable from PGO. The apparent 12 % win is entirely the GPU
governor deciding to run at a higher clock during those runs, not code layout.

Functional gate on the PGO build: compute 64/64, clear/resolve 262144/262144,
PASS. So PGO is *safe*, just not *faster* here.

## Why it didn't help

* The corpus exercises very few distinct shader compilations, so IR3 — the most
  CPU-heavy path in real games — received almost no profile counts and was left
  essentially unoptimized.
* Command-submission code is already tight and branch-predictable; there is
  little for a profile to rearrange.
* The benchmarks are partly GPU-bound even at 64×64 (4000 rasterised triangles),
  which masks CPU-side differences.

## What would make PGO worth revisiting

A corpus of **hundreds of distinct pipelines** (a few representative DXVK shader
sets compiled through Turnip), plus a CPU-only command-recording benchmark that
never submits to the GPU. With those, PGO would target IR3 and descriptor code
directly. Until then, the honest recommendation is: do not ship a PGO build, and
do not claim a speedup.

## Reproduce

Cross files and build dirs are generated by
`build/cross-pgo-instr.txt` / `build/cross-pgo-use.txt` (see the commands in
this document's method section); the merged profile lives in
`build/pgo/merged.profdata`. Nothing from this experiment is part of a release.
