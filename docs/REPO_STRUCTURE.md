## What belongs in git — and what does not

**Commit:**

* patches (small, reviewable, the actual delta from Mesa)
* build and packaging scripts
* probe/test sources (evidence and reproducibility)
* docs, pinned versions, licence files
* CI workflows and issue templates

**Never commit:**

| Path | Why | Where it lives instead |
|---|---|---|
| `src/` (Mesa tree, NDK) | hundreds of MB, generated by `versions.env` | downloaded by the build script; CI caches the NDK |
| `build/` | object files, `build.ninja`, absolute paths | regenerated |
| `dist/*.zip` | binary blobs bloat the history forever | GitHub **Releases** (assets), checksums attached |
| `tools/py/`, `tools/glslang/`, `tools/bin/` | installed toolchain wheels/binaries | pip / release download |
| `research/` | scratch downloaders and one-off probes | not published |

`.gitignore` enforces this. Keep `dist/` as a local output folder only.

## Releases and versioning

* Tag format: `v<mesa>-a22.<n>` — e.g. `v26.3.0-a22.1`.
* Each release attaches:
  * `turnip-a22-26.3.0-variantA.adpkg.zip`
  * `turnip-a22-26.3.0-variantB.adpkg.zip`
  * `SHA256SUMS.txt`
  * short release notes: what changed, validation performed, known issues
* `packageVersion` inside `meta.json` is bumped per release so front-ends can
  distinguish two builds of the same Mesa version.
* Never re-upload a changed binary under an existing tag; cut a new tag.
* Tag pushes trigger the build workflow only. Publishing is manual
  (`workflow_dispatch` or `gh release create`) so the validated local artifacts
  can be the ones users download.

## Branches

* `main` — always builds.
* `topic/<name>` — one branch per change (new Mesa base, new patch, tuning).
* Optionally `mesa/26.3` maintenance branch if you support multiple Mesa bases;
  keep patches per-branch, because `freedreno_devices.py` moves quickly.

## Suggested repository metadata

* **Name:** `turnip-a22` (short, searchable). Avoid "snapdragon-g2-gen-2-turnip-custom-driver".
* **Description:** `Mesa Turnip (Vulkan) driver packages for the Snapdragon G2 Gen 2 / Adreno A22 handheld, built and validated on real hardware.`
* **Topics:** `turnip`, `mesa`, `adreno`, `vulkan`, `adrenotools`, `snapdragon`, `retroid-pocket-g2`, `android`, `winlator`, `eden-emulator`.
* **Releases only for binaries**, README points to them; no LFS needed.

## Publishing checklist

```bash
git init
git add .
git commit -m "Turnip A22: Mesa 26.3.0 packages for Snapdragon G2 Gen 2"
git branch -M main
git remote add origin git@github.com:<you>/turnip-a22.git
git push -u origin main

git tag -a v26.3.0-a22.1 -m "Turnip A22 26.3.0 (A/B)"
git push origin v26.3.0-a22.1     # tag only; publishing stays manual
```

Publishing is a separate, deliberate step so a hand-tested build can be the
thing users download (a tag build would otherwise race the local artifacts):

```bash
# Option 1: attach the locally validated packages
gh release create v26.3.0-a22.1 \
  dist/turnip-a22-26.3.0-variantA.adpkg.zip \
  dist/turnip-a22-26.3.0-variantB.adpkg.zip \
  dist/SHA256SUMS.txt \
  --title "Turnip A22 26.3.0" --generate-notes

# Option 2: let CI build and publish from the tag
gh workflow run release.yml -f tag=v26.3.0-a22.1
```

Before tagging, confirm:

- [ ] `./scripts/build_turnip_g2gen2.sh` succeeds from a clean checkout
- [ ] both zips install and boot in at least one front-end
- [ ] `sha256sum dist/*.zip` matches the attached `SHA256SUMS.txt`
- [ ] README "Validation" section reflects the current run
- [ ] `versions.env` pins the exact Mesa/NDK used
- [ ] no `src/`, `build/`, `dist/*.zip` staged (`git status`)

## Why this shape

* **Patches, not a fork.** Two files changed; a fork of Mesa would rot within
  weeks. Patches make the delta auditable and rebase cheaply.
* **Evidence lives with the code.** The probe/test sources are what justify the
  "validated" claim; without them the README is marketing.
* **Binaries out of git.** A 14 MB `.so` re-packed every release would dominate
  repository size; Releases keep history small and give checksums for free.
* **Pinned inputs.** `versions.env` + `MESA_SHA256` make builds reproducible and
  let CI cache correctly.
